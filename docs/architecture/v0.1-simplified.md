# OrchMesh v0.1：基于 Pi 的多用户 Web 工作台

> 实施状态更新（2026-10-26）：登录、Pi RPC、SSE 和停止骨架已实现；实际结构与验收以 [实施记录](../development/implementation.md) 和仓库 README 为准。下文保留设计/工具调研背景。
状态：2026-10-26 调研后的建议方案，尚未实现；用户已确认使用者为本人和少量熟人，Pi 提供 Agent Loop，并保留 Shell、文件读写。其他范围与实现选择为本方案建议，不代表已验收。

## 1. 产品边界

首版完成：管理员开通账号 → 登录 → 创建聊天 → Pi 执行工具 → 流式展示 → 停止执行 → 再次打开历史。

每个用户有自己的执行环境和文件。多个聊天可以复用该用户的文件，但历史分别保存。建议每位用户同时只运行一个聊天，其他聊天可查看，不做后台任务排队。全局并发设上限，忙时明确拒绝，避免悄悄排队和重复执行。

暂不实现企业组织、Workspace 权限层、Agent 广场、跨用户 Agent 调用、A2A、多 Runtime、计费、工作流编排。Agent 首先是 Pi 的配置预设，而不是发布、版本、安装、授权四套系统。模型、工具和系统提示词的编辑界面可在基础聊天之后加入。

## 2. 最小架构

```text
浏览器：React + TypeScript + Vite
       │ HTTP 命令 / SSE 事件
FastAPI：登录、资源归属、会话索引、Pi 进程管理（单应用进程）
       ├── SQLite：用户、登录会话、聊天索引、执行摘要
       └── Pi RPC：stdin/stdout JSONL，经容器执行接口连接
            ├── 用户 A 容器：Pi + 用户 A 文件/会话
            └── 用户 B 容器：Pi + 用户 B 文件/会话
```

不新增 TypeScript 中转服务。Python 直接使用 Pi 官方支持的 RPC；Node 只作为 Pi 的运行依赖存在。Pi 接入模块负责进程、RPC 响应关联和生命周期，不实现模型循环、工具调度或上下文压缩。[RPC 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)

前后端源码分目录，生产环境合并为一个 Web 应用：Vite 构建出的页面资源由 FastAPI 托管，页面、API、SSE 同源，不单独运行前端 Node 服务，也不要求 Nginx。Node 在开发/构建阶段另用于前端工具链。完整目录与技术选型见 [项目蓝图](project-blueprint.md)。

API 内维护异步执行管理器，生命周期独立于某个 HTTP/SSE 请求。生产环境明确只启动一个应用 worker，不使用开发热重载；需要多实例或服务重启后仍持续运行时，再拆独立执行服务。

## 3. 直接复用与平台职责

| 能力 | 归属 |
|---|---|
| Agent Loop、模型接入、内置 read/bash/edit/write | Pi |
| 工具循环、上下文压缩、模型请求重试 | Pi |
| 会话 JSONL、继续会话、分支 | Pi；首版 UI 不必暴露分支 |
| MCP Client、Skills、扩展加载 | Pi；平台先维护受控配置 |
| 用户登录、聊天归属、容器映射 | OrchMesh |
| RPC → Web 事件、停止按钮、进程回收 | OrchMesh |

详细证据见 [Pi 能力调研](../research/pi-capabilities.md)。复用能力不等于首版全部暴露；扩展的交互弹窗也不会自动成为 Web UI。

## 4. 数据只保存一份权威内容

SQLite 放在宿主应用私有目录，建议仅存 `users`、`login_sessions`、`conversations`、`runs`。聊天索引保存 owner、标题、Pi session ID、服务端生成的文件定位信息和配置快照；执行摘要保存请求去重 ID、状态、开始/结束时间和错误原因。

Pi JSONL 是模型会话和工具记录的权威来源，不再同时维护一套 SQL messages/工具历史。平台通过 Pi 会话接口读取；需要加载磁盘会话时也必须经过同一执行管理器，避免打开正在写入的会话形成第二个写入者。数据库、JSONL 和用户文件均纳入备份。

SQLite 用于单机少量用户的元数据，不逐 token 写库；开启外键，采用短事务。SQLite 适用于低到中等流量网站，但大量并发写入、多台应用机器共享存储时应重新评估数据库。[SQLite 适用范围](https://www.sqlite.org/whentouse.html)

## 5. 会话与执行语义

1. API 校验会话 owner、请求去重 ID、用户执行锁及全局限额。
2. 在该用户容器内启动/复用绑定该会话的 Pi RPC 进程，先订阅事件再发送 prompt。
3. `prompt` 的成功响应仅表示受理；按实际 disposition 处理未启动执行的请求。启动后的结束判断使用 `agent_settled`，并结合错误/取消结果，不能把 `agent_end` 一律当成功完成。
4. 持续消费 stdout，即使没有浏览器订阅也不能停止读管道。stderr 单独收集，限制日志大小并避免暴露凭据。
5. 浏览器关闭：默认继续执行。重新连接：获取历史/当前状态并订阅后续事件。首版不承诺逐 token 持久化重放；用有界内存事件缓冲与序号处理订阅衔接，缓冲失效时重新同步快照。
6. 停止：若存在待处理输入，先 `clear_queue` 再 `abort`，等待实际结束；显式 RPC bash 使用对应的 `abort_bash`。超时终止 Pi，必要时停止该用户执行容器以清理遗留 Shell 子进程。停止不撤销已写文件或外部操作。
7. 服务/容器重启：清理残留执行，将未终结 runs 标记为 interrupted。恢复已有聊天，交由用户决定下一步，不自动重跑有副作用的命令。

Pi 自身的模型请求重试和平台重放整个业务执行不是同一件事。平台请求去重也不能保证外部操作恰好执行一次。[RPC 生命周期](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)

## 6. Shell 与文件的实际边界

建议管理员为少量用户预建独立容器，按需启动；每个容器只挂载本用户目录、会话和配置，Pi 使用非 root 身份运行。整个 Pi 进程都在容器中，不能只把 bash 工具放进容器。`cwd` 和工具名称允许列表不构成操作系统权限边界。[Pi 安全文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/security.md)

初期可由宿主上的专用应用账号通过容器引擎的 exec 接口管理 RPC，使用参数数组而非 shell 拼接；容器 ID、路径和启动参数全部由服务器映射，浏览器不能提交任意 Docker 命令。优先评估 rootless Docker，具体可用性在部署验证时检查，不在调研阶段改动系统。[Rootless Docker](https://docs.docker.com/engine/security/rootless/)

容器管理权仅属于可信后端；它仍能影响自己管理的全部用户容器，这是明确的信任边界。Pi 容器不挂载 Docker socket、宿主 HOME、平台数据库或其他用户目录。设置内存、CPU、PID 限额，禁用 privileged/host network，并控制到宿主与内网敏感服务的网络访问；仅分容器不能自动阻止网络访问。

Pi 的 `PI_CODING_AGENT_DIR` 和 session 路径单独设置，不继承开发者的 `~/.pi/agent`、扩展和凭据。Shell 可读取同环境的凭据；进入容器的模型/MCP 凭据必须视为该用户可用、可能可读的凭据。不要把管理员通用凭据藏在环境变量里就当作隔离。首版建议按用户配置独立限额凭据。

用户文件下载接口从归属校验后的目录解析路径，并处理路径穿越和符号链接。容器内的同一用户各聊天不做安全隔离；聊天记录也不是不可篡改审计日志。

## 7. 目录与技术选择

```text
apps/web/                         # React Web UI
apps/server/src/orchmesh/
  main.py                         # FastAPI 和应用生命周期
  auth/                           # 登录、用户身份
  conversations/                  # 归属、历史、请求与 SSE
  pi/                             # RPC、执行生命周期、容器接入
  storage/                        # 元数据及文件定位
apps/server/tests/
deploy/                           # Pi 镜像、部署配置
docs/research/
docs/architecture/
```

具体依赖与维护状态以[项目蓝图](project-blueprint.md)为准。后端复用 FastAPI 原生 SSE、SQLAlchemy async/aiosqlite、Alembic 与 SQLite；认证建议 FastAPI Users 的 CookieTransport + DatabaseStrategy，明确接受其维护模式，并单独验证 CSRF 与限流。前端复用 assistant-ui 外部 Runtime；Query 保存服务器快照，Zustand 构建当前活动视图，assistant-ui 只消费该视图。首版管理员开账号、同源 Cookie 登录，不开放公开注册/密码找回系统。

删除第一版独立 Worker、Redis/Taskiq、事件总线、Outbox、S3/MinIO、通用 Runtime 注册中心。文件保存在本地用户卷。以上简化以单机、少量熟人、允许服务重启中断执行为前提。

## 8. 开工前验证与扩展触发条件

先做小型接入验证：RPC 流式输出与工具事件、请求失败、abort、重连、Pi 异常退出、会话恢复、两用户文件不可互读、容器内无法访问平台凭据。扩展交互必须明确支持或禁用，避免确认请求永久挂起。测试需覆盖重发 prompt 不造成第二次执行和后台 Shell 清理。

这次调研没有运行真实模型、Shell Agent 任务或容器隔离实验，尚未验收上述行为。固定 Pi 版本后跑兼容性验证再实现 UI；当前本机 1.3.0 不是自动跟随上游 latest 的理由。

只在出现对应需求时扩展：需要跨重启持续执行 → 独立执行服务；需要多人同时编辑共享资源 → 协作与权限模型；需要跨机器部署/高并发写入 → PostgreSQL；需要业务 Agent 互调 → 再设计调用授权与 A2A；需要不受信任公众用户 → 重新评估隔离和网络治理。
