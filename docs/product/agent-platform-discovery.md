# OrchMesh 智能体平台需求规格（讨论稿）

状态更新（2026-10-27）：用户已授权正式迁移，核心实现和旧数据导入已完成，正在进行产品级验收。以下保留设计目标；实际完成项、证据与未完成门槛以[迁移验收报告](../development/platform-acceptance.md)为准。

本文件是此次需求变更的主记录。标为“已确认”的内容来自用户选择；“建议/待确认”不作为已批准需求。当前已实施核心迁移；本文件记录完整需求，不能把尚未落地的目标当作已有功能。术语见 [GLOSSARY.md](../../GLOSSARY.md)，方向取舍见 [ADR-0001](../adr/0001-agent-platform-and-on-demand-execution.md)。

## 1. 产品目标与首版范围（已确认）

把产品中心从“每用户长期代码执行工作区”转向“通过自然语言创建、发布和使用智能体”。长期助手依靠持久保存的聊天与记忆延续体验；代码执行按需分配临时沙盒，不要求每用户持有常驻容器。

首版面向本人及受邀用户，不开放公众注册。支持智能体广场、评论、自主协作和文件交付。默认统一助手接收用户需求并自主寻找协作者，也允许从广场直接与指定智能体聊天。

首版不做预编排、流程编辑器、外部 A2A 服务接入、定时或外部事件主动触发。外部操作权限系统暂不设计；对应首版工具范围限于搜索、读取、知识检索、文件处理和临时代码执行，暂不接入邮件发送或业务系统修改等外部写入工具。

## 2. 角色、对象与状态归属（已确认）

| 对象 | 定义与归属 |
| --- | --- |
| 使用者 | 发起任务，持有自己的聊天、记忆、输入文件和交付成果 |
| 发布者 | 创建和维护智能体；其他使用者不能修改其定义 |
| 管理员 | 具有修改智能体的权限；具体管理操作与下架规则待细化 |
| 智能体定义 | 可反复使用的职责、工具、知识来源和行为规则，不承载使用者的私有运行状态 |
| 草稿 | 尚未确认发布的定义，可修改和试运行 |
| 发布版本 | 经确认可供调用的一份定义；修改产生新草稿和新版本 |
| 对话 | 使用者与助手的交互记录，可跨多次任务延续 |
| 任务执行 | 某次具体工作的独立上下文、过程、调用关系和成果 |
| 记忆 | 用户偏好、用户与特定智能体的专属记忆；独立于运行实例保存 |
| 共享知识 | 作者明确提供给使用者共同使用的内容，不能隐含包含作者私人数据 |
| 临时沙盒 | 代码执行所需的短期环境，不是智能体身份、聊天或记忆的存储主体 |

同一个智能体可同时被多个用户调用；同一智能体也可处理不同任务。“智能体无状态”指共享定义不持有各次调用的私有状态，不代表对话、任务执行或记忆无需持久保存。

## 3. 智能体创建、发布与维护（已确认）

### 创建链路

1. 用户用自然语言描述希望创建的智能体。
2. 平台使用内部创建工具和提示词，以 grill me 式访谈澄清需求。
3. 形成可编辑草稿，明确职责边界、工具、知识来源和行为规则。
4. 完成一个用户认可的示例任务试运行，向用户展示结果。
5. 用户确认后发布至智能体广场；不能把草稿生成成功当作已发布。

创建工具只服务于创建流程，不自动赋予生成的智能体。用户所说的内部工具与提示词，在技术设计时需要盘点实际资产；当前不假定仓库已具备完整创建器。

### 发布与编辑

- 其他用户可以使用和评论智能体，修改权属于发布者和管理员。
- 发布后编辑产生新草稿，确认后发布新版本。
- 正在执行的任务保持原版本，新任务使用新版本。任务后续新选协作者时如何绑定版本，属于待细化的设计规则。
- 不随发布共享私人聊天、记忆或凭据。
- 复制、评分、关注、推荐排行、收费市场、下架和删除等能力尚未确认，不自动纳入首版。

## 4. 自主协作与重复工作（已确认）

### 发现与委派

- 基于 A2A 支持智能体间协作，首版仅发现本平台已发布且当前用户有权使用的智能体。
- 发现、选择、委派全部交由 Agent，自主调用协作者无需用户逐次确认。
- 预期的“收集资料 → 分析 → 生成报告”描述工作内容，不固化为流程图或指定执行顺序。
- 主 Agent 按需传递任务材料、必要上下文、调用记录与获授权文件，不直接开放用户全部历史、私人记忆或凭据。

### 调用可见性与复用

- 被委派智能体须了解父级及更高祖先调用其他智能体的情况。
- 避免重复做同一件事，不禁止多次调用同一智能体。
- 同一工作进行中时等待或补充需求，已完成时优先复用结果，失败允许重试。
- 同一智能体处理不同目的的工作，应视为不同任务，允许并发。
- 调用记录和结果复用限定在同一使用者的一次根任务内，包含相关同级分工；跨用户不复用私人任务结果。记录字段与并发协调机制留待设计。仅把历史放入提示词不能保证两个 Agent 同时委派时不会重复。
- 找不到合适协作者时，优先由现有助手处理；确需新能力时进入私有草稿创建流程，发布仍需用户确认。

### 额度

首版不设固定协作深度、次数、每任务费用/时长或每用户用量额度。平台统一配置模型并承担费用。本条取代早期提出的每用户额度建议；不自行重新加入产品额度。部署容量与故障处理另行设计，不宣称物理资源无限。

## 5. 知识与长期记忆（已确认）

### 知识来源

首版支持作者提供的文件、文本和公开网页；任务过程中也允许使用者上传材料。企业数据库和内部知识系统接入后续再考虑。作者共享知识与任务私人材料必须区分，上传任务材料不等于发布给广场使用者。

### 记忆

- 支持用户明确提出“记住这个”。
- 允许 Agent 从交互中提取稳定偏好，不将每段聊天都视为长期记忆。
- 分开保存用户通用偏好与用户对特定智能体的专属记忆。
- 用户可以查看、修改、删除和关闭记忆。
- 记忆不放入共享智能体定义，也不因发布者修改定义而共享给其他用户。

关闭记忆是否停止读取既有记忆、删除如何影响历史聊天、引用与缓存，需要在具体设计中说明，不能以只隐藏界面替代删除语义。

## 6. 临时执行与文件交付（已确认）

- 仅在任务需要执行代码时申请临时沙盒，不因登录、聊天或浏览广场就为每用户固定分配执行容器。
- 首版任务工具包括搜索、网页读取、知识检索、文件处理和临时代码执行。
- 上传文件和交付成果独立持久保存，供查看、下载和后续任务按授权取用。
- 临时中间文件默认不保留；回收沙盒不能删除已交付成果。
- 首版实施采用任务级 Docker 与官方 DSH SSH 工具，按需创建并在执行阶段结束后释放；保留工作文件供恢复。
- 需要恢复长任务时，哪些执行状态属于恢复材料不能简单归为可删除的中间文件；与第 7 节一起设计。

## 7. 任务失败与重启恢复

### 首版必须具备的能力（已确认）

用户本轮明确要求首版包含重启恢复，取代之前“显示中断并由用户重试即可”的最低承诺。任务需要在 Host 或平台服务重启后，根据已保存状态重新接管并继续未完成工作，而不要求用户从头描述或手工重新派发整项任务。

恢复的是任务目标与工作进展，不承诺复活原模型网络流、原进程内存或原 Shell 调用栈。官方可恢复状态、需要重新驱动的部分与结果未知的工具操作须分别处理。不能确认是否完成的操作不得直接伪装为成功，也不能无条件重放；需核对保存结果，确实无法自动处理时明确展示阻塞原因及需要的输入。

### 首版恢复验收要求（由上述目标推导）

| 场景 | 应有结果 |
| --- | --- |
| Host 或平台服务重启 | 自动找到未完成任务，重新建立执行对象并继续工作；用户可查看恢复状态 |
| 输入已接纳、尚未执行 | 找回已接纳输入，避免丢失或重复入队 |
| 已开始的任务中断 | 从持久进度重建上下文，已完成工作优先复用，不把整项任务当成新任务从头派发 |
| 子任务完成但父级尚未收到 | 找回子任务结果，并让父级继续；不能重复委派同一工作来补通知 |
| 工具结果未知 | 区分未开始、已完成、结果未知，核对可用产物或执行记录后决定继续或重试 |
| 发布版本发生更新 | 原任务恢复仍采用绑定版本，不因重启静默切换至新定义 |
| 临时沙盒已丢失 | 使用保存的输入与必要恢复材料建立新沙盒；不要求原进程还活着 |
| 恢复过程再次中断 | 重复接管不导致同一业务工作被多个执行者同时重复执行 |

运行框架的机制与平台需提供的最小适配以实验为准，不提前选定额外工作流引擎。不能以固定“继续”提示词无条件重发代替任务恢复设计。

### 官方能力核查与隔离实验结论（非平台恢复验收）

- DSH 不只是保存聊天：已有 Session 事件持久化、Agent 重建、持久 inbox，以及本地子智能体目录和冷恢复能力，可作为复用基础。优先保留官方 `session-checkpoint-policy` 的落盘检查点，不在平台重写一套同等检查点。
- Agent 恢复会修复未完成 turn，并区分工具尚未开始与工具结果未知；不能把恢复历史理解为原调用栈继续执行，也不能把结果未知的工具一律重放。未完成的流式增量可能尚未形成持久消息，首版不承诺每个已显示 token 都能恢复，恢复基于已提交进展。
- 官方 jobs-local 不恢复正在执行的 Shell/进程。平台仍需保存业务任务身份、原智能体版本和父子委派关系，并决定重启后如何接管、核对成果及继续任务。
- 官方子智能体冷恢复可能使用当前 preset；新平台要求的原版本固定不能直接假定已由 DSH 保证。
- 官方问题恢复有 timed/continued 路径，当前平台的 blocking 提问与进程内 pending Map 不能直接套用该能力。

研究见 [DSH 持久化与重启恢复](../research/dsh-persistence-and-restart-recovery.md)，包含固定源码引用与 rc.3 发布包核对范围。本轮在独立临时环境使用 rc.3 官方发布包、官方检查点插件及确定性模拟模型完成六类 SIGKILL 后重建实验：正常历史、流式中断、双工具中断、未领取输入、已完成子任务、执行中子任务，六类均通过预定断言。记录见 [官方恢复接口实验](../research/dsh-restart-experiments.md)。恢复后的根 Agent 在观察窗口内保持 idle，实验通过显式 followup 再次驱动，没有重复投递原排队输入；子任务通过官方 sendMessage 冷恢复。

实验验证官方原语，不等于平台自动接管功能已实现。目前正式应用已完成父子任务中断、版本冻结、双用户隔离和提问恢复验收；精准窗口与剩余边界见迁移验收报告。恢复验收必须实际终止并重启 Host/服务；正常结束后重新打开历史不能替代这项测试。

## 8. A2A 与现有实现的边界

官方 Agent Card 描述对外能力、接口与认证要求，不等于内部完整定义。A2A 支持发现入口及目录模式，但不规定目录标准 API；广场、检索和协作者选择策略仍需平台明确。A2A 的任务、流式与异步接口不自动提供用户记忆或后端重启续跑。

来源：[官方发现指南](https://a2a-protocol.org/latest/topics/agent-discovery/)、[任务生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)、[流式与异步](https://a2a-protocol.org/latest/topics/streaming-and-async/)。实施时另行固定协议与 SDK 版本。

当前仓库锁定 DSH `0.2.1-rc.3`。已有身份认证、聊天、流式消息、文件预览/下载和运行交互可作为复用候选，但不能因此认定新的 Agent 产品模型已存在。现有 DSH Agent 是运行对象，Project 是文件目录与 Workspace 登记。当前导航、历史读取和执行都依赖用户 Host；只删除登录预热不能完成转型。现有 `Manager.recover()` 清理旧容器并把运行标为 `interrupted`，没有自动续跑逻辑。

## 9. 验收清单草案（由已确认需求推导，未执行）

| 场景 | 可观察结果 |
| --- | --- |
| 自然语言创建 | 访谈后得到可编辑定义；职责、工具、知识来源、规则明确 |
| 发布前验证 | 示例任务完成并展示结果，用户确认前不出现在广场 |
| 发布维护 | 发布者与管理员可编辑；普通使用者能调用和评论但不能修改定义 |
| 版本隔离 | 定义更新不改变已开始任务采用的版本 |
| 自主协作 | 统一助手按需要选用已发布协作者，无需逐次确认，无预编排流程 |
| 调用上下文 | 子任务能看到父级及祖先的相关委派情况 |
| 同工作复用 | 已进行/完成的同一工作可等待或复用，失败可重试；不同工作不误去重 |
| 多用户并发 | 两名用户同时使用同一个智能体，任务、聊天、私人记忆与文件不串用 |
| 记忆管理 | 明确记忆与自动偏好可查看/修改/删除/关闭，跨次任务可按设定取用 |
| 临时执行 | 不需要代码的交互无需固定用户沙盒；代码任务结束回收后交付物仍可下载 |
| 报告任务 | 自主收集资料、分析、核对并交付下述报告及来源文件 |
| 重启 | 自动接管未完成任务，复用已完成子任务结果，继续产出成果；具体故障点见第 7 节 |

建议补充故障测试：Agent 与工具执行途中退出、子任务已完成但父任务尚未接收、待答问题未提交、两个委派并发命中相同工作、交付文件落盘但完成通知丢失。测试结果需区分官方运行时、平台适配与真实模型验收。

### 首个具体验收任务

用户已接受报告型验收方向，并授权其余问题按建议推进；选取与本项目相关、可通过公开一手资料核验的实例：

> 根据 A2A 与 MCP 官方规范及官方 SDK 文档，生成一份“内部智能体平台中 A2A 与 MCP 的职责分工”调研报告。说明各自解决的问题、组合使用方式、能力边界及不确定项，给出可核验来源，并交付可预览和下载的报告文件。

- 输入：任务说明、官方文档范围、核查日期。模型凭据与私人聊天不作为报告素材。
- 准备：通过创建流程发布资料研究、事实核对、报告写作等可选能力；由助手自主选择协作者，不固定步骤、人数或执行顺序。
- 交付：`report.md`、可预览的 `report.html`、记录来源链接与核查日期的 `sources.json`。
- 成功标准：重要事实能追溯到来源；事实、推断和未知明确区分；无伪造引用；任务过程可观察、交付文件可下载；重复请求同一工作可等待或复用结果，不阻止同一智能体执行不同任务。
- 并发验收：两位使用者同时调用同一发布版本，内容、记忆、文件和委派结果不串用。
- 恢复验收：在研究中、子任务已完成但父级未接收、代码生成报告中分别中断运行，再验证重建与继续；确认已完成工作不被整项重做。先用可计数的模拟模型/工具构造可重复故障，再用真实模型验证业务链路。

这是一项验收实例，不是引入预编排模式，也不是新增智能体调用额度。

## 10. 待验证的技术边界与后续细节

此前 P1–P4 已收敛：首版要求恢复；去重限同用户同一根任务并包含相关同级分工；缺少能力时优先现有助手、必要时创建私有草稿；采用上述报告任务验收。不得继续将这些标为未确认产品方向。

| 项目 | 当前需要解决的问题 | 处理方式 |
| --- | --- | --- |
| 官方恢复能力 | resume 后哪些状态自动恢复、哪些需要公开接口重新唤醒，哪些根本不能恢复 | 本轮隔离进程实验，分别记录通过、失败、未测 |
| 自动任务接管 | 平台服务重启后如何找到任务、避免重复接管、对账已有结果并继续 | 优先复用官方任务/会话服务；仅补其没有承担的平台职责 |
| 发布版本绑定 | 子任务冷恢复不得采用已更新的 preset | 设计版本身份与官方恢复接口之间的映射，实测旧版本重建 |
| 去重协调 | 同级并发委派同一工作、结果已完成但通知丢失如何处理 | 利用可持久追溯的调用关系与结果身份，不单靠模型提示词 |
| 恢复材料 | 临时沙盒丢失后恢复所需文件如何区别于可丢弃的临时文件 | 定义保存时点、任务归属与清理条件，保留官方已有持久结果 |

后续交互设计还需说明：记忆关闭/删除的具体语义、知识更新与版本关系、智能体下架规则、多智能体版本绑定时点、用户停止与恢复入口、原有账号/聊天/项目文件的迁移方案。这些细节尚未批准，不应静默扩大功能范围；有实现事实可查的部分由开发者核查，不让用户猜接口行为。

技术选型留待验证结果：DSH 的保留或替换、A2A SDK、目录搜索、去重协调、记忆存储、沙盒及任务恢复适配。优先官方公开接口和成熟实现，不自行重写 Agent Loop、消息持久化、输入队列或已有的子任务恢复机制。应用代码仍保持不动。
